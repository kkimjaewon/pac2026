# FR3 C HAL 이동 오류 수정 및 검증 — 2026-10-06

## 결과

실제 B(rt_control) → 수정한 C → Gazebo FR3로 동일 경로를 재시험했다.
수정 전에는 8개 목표 중 5개만 도착하고 수직 하강·중앙 복귀·물체 이동 보정이 실패했다.
최종 수정 후 8개 모두 도착했으며 이동 중 관절 제한 오류는 0회였다.
그러나 IK 500μs 시간 초과 1회, 철판 순간이동 후 STATE_STALE 1회가 남았다.
두 오류 모두 보호 정지/복구 후 도착했다. 오류 없는 실시간 운전을 달성했다고 주장하지 않는다.

## C에서 수정한 것

1. IK 내부 수렴 정밀도를 1e-7 → 1e-9로 개선했다.
   작은 목표가 여러 주기 동안 같은 관절 해로 양자화되고 이후 한 번에 갱신되어,
   실제로 부드러운 입력에서도 관절 가속도 초과를 만들던 문제를 수정했다.
   동일한 20,000개 수직 목표와 0.7/1.3ms 교대 간격 시험에서
   가속도 초과는 65 → 0회, 최대 가속도는 1.93354 → 0.0536109rad/s²였다.
2. 불균일 간격의 가속도를 `2*(v_new-v_old)/(dt_new+dt_old)`로 계산한다.
   구간 평균 속도의 시간 위치를 반영한다. 명령 누락이나 주기 변동 때 현재 간격만으로
   나눠 가속도를 잘못 판단하던 부분을 수정했다.
3. 관절 제한 오류에 관절 번호, 두 시간 간격, 속도·가속도와 변화량을 기록한다.
4. IK 입력/결과 배열을 재사용한다. 시간 초과에는 wall 시간, thread CPU 시간,
   solver 반환값을 기록한다. 500μs 제한과 5ms TTL은 유지한다.
5. 신선한 측정/수신 상태가 복구되면 STATE_STALE·DISCONNECTED를 즉시 해제한다.
   heartbeat도 명령 수락과 같은 healthy 조건을 사용한다.
6. 수신 상태의 신선도는 실제 sampled_mono_ns로 계산한다.
   늦게 도착한 상태에 수신 시각 기준으로 신선도 기간을 다시 부여하지 않는다.

관절 속도 0.5rad/s, 가속도 1rad/s², 세션/순번 검사와 watchdog을 완화하지 않았다.
C 단일 executor에서만 변환기를 사용한다. 재사용 배열은 동시 inverse 호출용이 아니다.

## 실제 구동 시험 조건과 결과

- FR3 Gazebo, 공구/hand 없음, map→base 항등, flange→TCP offset=0.
- 팀 B 소스 변경 없음. 시험 A가 최종 TCP 위치를 발행했다.
  실제 A의 영상 검출 및 B의 z+0.10 처리 구현을 검증한 것은 아니다.
- 충돌 없는 높은 초기 관절 자세에서 시작했다.
- TCP 중심 (0.35,0,0.81), 아래를 보는 초기 측정 자세 유지.
- B v_max=0.01m/s, a_max=0.01m/s². 전체 범위 시험의 accept_radius=0.10m.
  실제 운영용 0.05m 허용 반경 시험과 구분한다.
- 목표: x=0.40/0.30, y=±0.05, z=0.86/0.76, 중앙 복귀,
  실제 철판 4.47cm 이동 후 TCP=(0.39,0.02,0.81).
- 도착: 위치 오차 2mm 안을 0.3초 유지. 최종 측정 오차 최대 약 0.00242mm.
  이 수치는 이상적인 Gazebo 측정값이며 실물 정확도 수치가 아니다.
- 이동 중 관절 제한 0회. IK 초과 1회: wall=710.864μs,
  thread CPU=700.203μs, solver_rc=0. 정상 해라도 시간 제한 초과로 폐기했다.
- 물체 순간이동 후 STATE_STALE 활성 이벤트 1회, 명령 거부 71회 후 복구.
  상태 지연의 원인이 gateway, Gazebo, DDS 중 어디인지까지 확정하지 않았다.
- A 중단 → B HOLD/마지막 목표 유지, C 수신 controller 비활성화 → FAULT,
  재활성화 + /rt/reset_fault → 세션42·순번 유지, B 종료 → watchdog 정지 통과.
- 3,714개 실제 관절 샘플(약20ms 간격) 환경 충돌 재검사: 충돌0,
  비스듬한 카메라와 최소 거리 약0.709m. 연속 경로·자기충돌·실제 공구 검증은 아니다.
- C 검사 46개 통과. 만료/재전송/범위/IK/급격한 관절 목표 차단 실제 시험 통과.

## 5cm 허용 반경의 추가 시연 시험

최종 C에서 accept_radius=0.05, v_max=0.01m/s, a_max=0.005m/s²로
수평±4cm·중앙·실제 철판 4.47cm 이동 보정을 추가 시험했다. 6개 모두 도착했고
최종 오차는 약0.133~0.195mm, 관절 제한 오류는0회였다.
IK 시간 초과1회(wall=1318.85μs, thread CPU=35.688μs, solver_rc=0)와
철판 이동 후 STATE_STALE1회가 있었다. 전자는 CPU 계산보다 wall 지연이 훨씬 커
OS 실행 지연과 일치하며, 후자의 정확한 원인 분리는 남았다.
HOLD/FAULT/수동 복구/세션·순번 유지/watchdog은 모두 통과했다.
증거: logs/c-fix/demo-horizontal/report.json, B.log.

## 아직 해결되지 않은 범위

- 500μs IK 및 1kHz±100μs의 최악 시간 보장. 일반 Linux/Gazebo 환경의 가끔 발생하는
  시간 초과를 안전 검사로 감지·복구했지만 제거하거나 하드 RT로 보장하지 못했다.
- Gazebo 철판 순간이동 시 피드백 공백의 원인/최악 지연.
- 온라인 환경·자기충돌 방지와 실물 안전 진입 경로. READY는 충돌 없음의 보증이 아니다.
- 실제 공구 장착 후 TCP offset/충돌, 실제 A→B 높이 오프셋 연결.

## B 담당에게 요청

1. 철판 표면 위치로 계획 위치/accept_radius를 검사한 뒤 map z+0.10을 적용한다.
   계획 표면=(0.35,0,0.71), TCP 목표=(0.35,0,0.81)를 분리한다.
2. C의 E_SEND_FAILED(7)를 처리하도록 안전 오류 마스크에 추가하고 정책을 합의한다.
3. EXPIRED 빈도를 오류 활성 이벤트 횟수로 세지 않는다. 실제 C에서 10개 연속 만료를
   거부했지만 활성 이벤트는 1개였다. 명령별 거부 기록/카운터 규약이 필요하다.
4. 오류 해제 후 신선한 실제 TCP에서 재출발하는 기존 동작과 세션·순번 유지 동작은 유지한다.
5. v=0.05m/s, a=0.25m/s²는 별도 joint/path 검증 전 승인하지 않는다.

## 나현/A 담당에게 배치 제안

확인한 nahyun/world-plate-camera 원격 HEAD는 3cd76f6으로 여전히 낮은 책상/빨간 큐브였다.
따라서 전달받은 수치를 재구성한 검증 월드에서 시험했다. 최신 파일 커밋 확인이 필요하다.

- 원래 통짜 책상 (0.5,0,0.35), 1.0×0.8×0.7은 베이스/여러 팔 링크와 겹친다.
- 원래 TCP (0.5,0,0.81)는 중심 IK 성공, 수평 반경5cm 격자46/81만 IK 성공.
  실패는 이 solver·seed·고정 자세에서의 수치 결과이며 모든 IK 해가 없다는 증명은 아니다.
- 제안 상판 중심=(0.60,0,0.68), 크기=(0.90,0.80,0.04), 윗면z=0.70.
- 다리 중심 x=0.19/1.01, y=±0.36, z=0.33, 크기=(0.06,0.06,0.66).
- 철판 중심=(0.35,0,0.705), 크기=(0.30,0.20,0.01), 계획 표면=(0.35,0,0.71).
- TCP=(0.35,0,0.81), XYZ±5cm의 1cm 격자1,331개 IK·환경 충돌 검사 통과.
- 카메라=(0.35,-0.60,1.50), SDF RPY=(0,0.9212469047,1.5707963268).
  map→camera_link quaternion xyzw=(-0.3143136783,0.3143136783,0.6334089608,0.6334089608).
  SDF camera_link(+X 전방) 값이다. A의 optical frame 변환은 별도로 유지해야 한다.
  실제 영상에서 정수직 배치보다 팔의 가림이 줄었지만 A 검출 정확도는 미검증이다.

제안 배치에서도 기본 낮은 초기 자세는 충돌한다.
검증용 초기 q(rad)=(-0.0000005826,-0.3571429835,0.0000014681,-1.4191722009,
-0.0000038316,1.0620303777,0.7853970320)로 Gazebo를 초기화했다.
이것을 실물 로봇에 즉시 명령하라는 의미는 아니다. 별도 진입 경로 검증이 필요하다.
