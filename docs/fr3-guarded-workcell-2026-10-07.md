# FR3 C HAL: 작업대 충돌 방지와 접근·복구 검증 (2026-10-07)

후속 지연·복구 검증과 최신 실행 방법은 [추가 검증 보고서](fr3-delay-recovery-2026-10-07.md)를 참고한다.

이번 변경은 C HAL과 C에서 사용하는 별도의 제안 시뮬레이션 월드다. A/B 소스와 나현 담당 `pac_worlds` 월드는 수정하지 않았다. 10월 7일 원격 조회에서 `nahyun/world-plate-camera`는 여전히 `3cd76f6`이므로 전달받은 최신 숫자가 포함된 원본 파일을 검증했다고 표현하면 안 된다. 아래 월드는 전달받은 요구와 이전 충돌 결과를 토대로 작성한 제안이다.

## 변경과 실행

- `scene_guard`는 공식 FR3 URDF 충돌 메시를 FCL로 검사한다. 책상·철판 이동 범위·카메라·다리·바닥, SRDF 예외 외의 자기 충돌을 검사한다.
- 실제 측정 자세가 충돌하면 HAL_FAULT/E_DEVICE로 명령을 막는다. 새 명령의 측정→이전 목표→새 목표 구간이 충돌하면 E_OUT_OF_RANGE로 거부한다. 장애물 여유는 5mm, 관절 구간 샘플 간격은 최대 0.002rad다. 너무 큰 단일 구간은 접근을 나누도록 거부한다.
- 전용 launch는 SDF와 검사 장면의 이름·형상·위치·회전·정적 여부를 대조하고 초기 관절 제한과 충돌을 검사한다. 불일치·미등록 장애물·위험 초기 자세는 Gazebo 생성 전에 실패한다.
- IK의 고정 6×7 SVD 연산으로 반복 계산 비용을 줄였다. IK 500μs wall deadline, TTL 5ms, 관절 속도/가속도 제한은 유지했다.
- C 자체의 `feedback_gaps.csv`에 콜백 간격과 Gazebo 시각/수신단 monotonic 시각의 간격을 함께 기록한다. 정상 구간 전체를 추가 기록하지 않고 20ms 초과 간격만 기록한다.
- `executor_cpu`와 `executor_fifo_priority`를 선택할 수 있다. 기본은 일반 스케줄링이다. FIFO를 요청했는데 권한이 없으면 실패한다. 시스템 권한을 자동 변경하지 않는다.

```bash
# 프로젝트 루트, 빌드된 ROS 환경에서. 기존 B/b_mock/Gazebo가 없는지 먼저 확인.
bash scripts/hal_ros_exec.sh ros2 launch pac_hal fr3_guarded_workcell.launch.py \
  session_id:=42 gui:=true
```

전용 launch의 초기 관절값은 Gazebo 초기화 값이며 실물 즉시 이동 명령이 아니다. 일반 `hal_simulation.launch.py`는 장면 파일을 명시하지 않으면 기존처럼 충돌 검사가 꺼진다. 전용 launch 또는 `collision_scene_file`을 사용해야 이번 보호가 적용된다.

## 팀에 제안하는 배치

| 항목 | map 기준 값 |
|---|---|
| 얇은 상판 | 중심 `(0.60,0,0.68)`, 크기 `0.90×0.80×0.04`, 윗면 z=0.70 |
| 다리 | x=0.19/1.01, y=±0.36, 중심 z=0.33, 크기 `0.06×0.06×0.66` |
| 철판 | 중심 `(0.35,0,0.705)`, 크기 `0.30×0.20×0.01` |
| A 계획 표면점 | `(0.35,0,0.71)` |
| B 최종 TCP | 표면점 z+0.10 → `(0.35,0,0.81)` |
| 카메라 | `(0.35,-0.60,1.50)`, RPY `(0,0.92124690465924,1.57079632679490)` |
| 카메라 quaternion xyzw | `(-0.31431367828262,0.31431367828262,0.63340896081793,0.63340896081793)` |

현재 공구/손이 없는 FR3, TCP offset=0, map/base 고정 조건이다. 철판의 ±5cm **XY** 이동을 장면에 포함한다. 실제 카메라 A 검출/TF와 공구 형상은 별도 검증해야 한다.

접힌 기본 초기 자세는 이 상판에서도 `fr3_link5 / tabletop` 충돌로 launch가 거부했다. 높은 대기 자세는 q=`[-0.4,-0.3571429835,0,-1.4191722009,0,1.0620303777,0.3853970320]`, 측정 TCP 약 `(0.322371,-0.136297,0.809991)`이다. 아래 보는 자세를 유지하며 다음 세 경유점을 순서대로 이동한다.

1. `(0.322371,-0.136296,0.86)`
2. `(0.35,0,0.86)`
3. `(0.35,0,0.81)`

더 멀리 접힌 대기 자세에서 같은 Cartesian 경로를 이용하면 다른 IK 팔 자세로 수렴해 팔꿈치가 철판 이동 범위와 겹쳤다. 이 경로는 실행하지 않았다. 손끝 좌표만으로 접근 안전을 판단하면 안 된다.

## 실제 구동 결과

ROS 2 Jazzy/Gazebo Harmonic, 실제 팀 B `rt_control_node`, C, FR3를 구동했다. A 대신 30Hz 검증 발행기를 사용했다. B의 높이 오프셋 구현을 검증한 것이 아니라 발행기에서 최종 TCP를 보냈다. C executor CPU=15, FIFO=0 조건이다.

- 접근 3/3 도착, 명령 오류 이벤트 0, Gazebo 로봇 접촉 0. 최대 도착 위치 오차 약 0.003mm.
- x/y/z 각각 ±5cm와 원점 복귀, 철판 XY 이동 4.47cm 후 추종까지 8/8 도착. 로봇 접촉 0. 이 시험은 1cm/s, 0.01m/s² 조건이다. 5cm/s, 0.25m/s²를 승인한 결과가 아니다.
- A 중단 → HOLD, 마지막 목표 유지. C 수신단 실제 비활성화 → 오류 8/9 및 FAULT. 활성화·수동 reset → 세션42/순번 유지. B 종료 → watchdog 속도0.
- 위험 목표 `(0.35,0,0.69)`는 `fr3_link7 / plate_motion_envelope` 충돌로 거부했다. 실제 접촉 0, 정지 위치 유지. 위험 목표의 미도착이 정상 결과다.
- 실제 접근 도착 관절값을 seed로 ±5cm 1cm 격자 1331점 모두 IK와 충돌 검사를 통과했다. 각 점까지 Cartesian 1mm 간격으로 경로를 나눠 검사했다. 이는 offline 공간 검사이며 IK budget=100ms로 설정했고, 생산 500μs deadline/전체 격자 실시간 동작을 검증한 결과가 아니다.
- 초기 자세/월드 불일치 검사와 기존 C 계약·FK/IK 검사 57개를 모두 통과했다.

검증 코드/원본 로그는 프로젝트 루트 `checks/c-fix`, `checks/world-validation`, `logs/c-workcell-fix`에 있다. 접근, full, collision 하위 폴더의 report.json이 각 시험 결과다.

## 아직 해결되지 않은 결과와 담당 요청

**일반 Linux 스케줄링 지연**: full 시험에서 IK wall 712.032μs/실제 thread CPU 36.884μs로 500μs 제한을 넘은 사건이 1회 있었다. 계산 비용 문제와 실행 중 선점 지연을 구분해야 한다. C 계산·제한·충돌 검사 합산 sent 구간은 전체 시험 median 약72μs, p99 약130μs였지만 max는 1ms를 넘었다. 1kHz±100μs 또는 오류0을 달성했다고 주장하지 않는다. 현재 호스트 CAP_SYS_NICE가 없어 FIFO 구동은 검증하지 않았다. RT 실행 환경에서 B/C/Gazebo 부하를 분리해 다시 측정해야 한다.

**Gazebo 철판 이동 시 상태 공백**: C에서 joint 콜백 gap 약100.8ms인데 sim stamp는 1ms 진행했다. 수신단 sample monotonic 자체도 약103.8ms 공백이었다. C 콜백만 늦은 것이 아니라 Gazebo 업데이트/수신단 상태 생성이 벽시계에서 멈춘 증거다. STATE_STALE 거부·정지·복구는 정상 작동했다. 물체 순간이동 시연에서 이 부하를 줄이거나 정지/신선한 상태 확인 절차를 합의해야 한다. freshness 제한을 무작정 늘리지 않는다.

**B 요청**:

1. A의 **표면점**으로 계획 위치/accept_radius를 검사한 뒤 z+0.10을 적용한다. 접근 단계의 경유점은 일반 ±5cm AI gate와 분리해야 한다. 검증 접근에서는 임시 accept_radius=0.65로 경유점을 허용했다.
2. deadline 사건 후 재개 시 관절3 가속도 1.197rad/s²(제한1.0) 명령이 실제로 거부됐다. C 보호를 유지하고 B limiter 재개 직후 위치/속도/가속도 연속성과 첫 두 출력, C seed/측정 정렬을 함께 확인해야 한다.
3. E_SEND_FAILED=7의 정지/FAULT 처리를 명시한다.
4. HalError는 active 변화 이벤트다. 지속 EXPIRED 10회가 10개 이벤트로 발행되는 구조가 아니므로, "1초10회"는 C `last_command_seq/last_command_result` 또는 별도 누적 카운터 계약으로 집계해야 한다.
5. C 단절 시연은 A 발행 중단과 순서대로 실행한다. 이번 실제 시험도 분리했다.

**나현/A 요청**: 제안 배치를 합의한 뒤 나현 원본 월드, scenario_config 표면 계획점, 카메라 TF를 함께 반영하고 실제 A 출력이 map 표면점과 일치하는지 확인한다. 최신 나현 원본과 실물 공구를 검증한 결과가 아니다.

샘플 검사와 5mm 여유는 연속 충돌 검증/실물 로봇 안전 인증을 대체하지 않는다. 가변 공구, 다른 동적 장애물, HA006B/UR5e는 이 FR3 장면 범위 밖이다. push/PR/병합은 이번 변경 검토와 사용자 승인 후 진행한다.
